# Q15–Q16 Release Assurance Assessment — 2026-11-23

Status: READ-ONLY DESIGN ASSESSMENT — NO BUILD, DEPLOY OR RELEASE
Base commit: `944d7cb70a5d59d53c8fb379752bbee2085f7c8c`

## Executive finding

CK-NEXUS already has candidate workflows for clean-machine validation and runtime license inventory/package assembly. These are useful foundations, but the current definitions contain fixed-subject assumptions and evidence limitations that must be resolved before they can be treated as reusable release assurance.

## Q15 — Clean-machine deployment

### Existing implementation

- `.github/workflows/candidate-automated-gates.yml` runs on GitHub-hosted `ubuntu-24.04`, performs a frozen `uv sync`, compile, Ruff, pytest and starts the unified runtime for health/control smoke checks.
- It emits a `PASS_CANDIDATE` record with runner/image metadata and elapsed duration.
- `scripts/gate_clean_machine.py` is intentionally fail-closed and still returns BLOCKED, requiring deployment-specific evidence.

### Gaps

1. The workflow installs from the checked-out source using `uv sync`; it does not install the exact release archive/package that would be delivered.
2. The clean-machine evidence is generated by an inline workflow block rather than the canonical fail-closed gate collector, so the evidence contract can drift.
3. The recorded elapsed duration starts before dependency installation but ends after runtime smoke; it does not separately record install, startup, health and smoke timings.
4. The workflow uses a GitHub-hosted runner, but does not attest the VM image identity beyond runner-provided strings or prove the exact artifact checksum consumed by the install.
5. Cleanup currently kills the recorded process but does not provide a structured cleanup receipt for all child processes, temporary files, containers or credentials.
6. A single successful smoke run does not establish supported-host coverage, upgrade/rollback behavior, or a reproducible install across fresh hosts.

### Recommended Q15 design

- Build a candidate archive once, record its SHA-256 and provenance, then install that exact archive on a new ephemeral VM.
- Separate build and install jobs; transfer only the immutable artifact and signed/verified manifest.
- Verify archive digest and provenance before extraction/install.
- Record OS image/runner metadata, architecture, package manager, dependency resolution, install/startup/health/smoke durations, process tree and cleanup.
- Use synthetic credentials only; prove no credentials persist after the runner is destroyed.
- Keep `scripts/gate_clean_machine.py` fail-closed until it validates a complete evidence bundle; do not change it to print PASS based on a marker alone.

## Q16 — Runtime licenses and final release package

### Existing implementation

- `.github/workflows/candidate-runtime-licenses.yml` builds a Docker image and inventories installed Python distributions, package metadata and detected LICENSE/LICENCE/COPYING/NOTICE files.
- `THIRD_PARTY_NOTICES.md` records a historical inventory of 55 distributions and 0 unresolved metadata/file-evidence entries for an older runtime subject.
- `.github/workflows/final-production-package.yml` verifies evidence provenance, checks Q10–Q16 records, re-runs release checks, builds an image, exports runtime license files and creates a checksummed source archive.

### Critical gaps

1. **Fixed expected subject:** the final package workflow hardcodes `EXPECTED_RELEASE_SUBJECT=96dcd0f...` and repeats that value in the package job. This makes the workflow unsuitable for a new candidate until the subject is deliberately rebaselined through an independently reviewed change.
2. **Evidence contract inconsistency:** the preflight accepts Q15 `PASS_CANDIDATE`, Q13 `status=PASS`, and Q16 image `PASS_CANDIDATE` while the final release wording uses production PASS semantics. Candidate/component results must not silently become production authorization.
3. **License evidence is heuristic:** presence of a `License` string, classifier or filename containing a license-related token is not proof that the detected license is correct, that all license texts are complete, or that obligations/notice requirements have been met.
4. **Hardcoded distribution count:** package assembly asserts exactly 55 distributions. This is brittle across legitimate dependency updates and can create false failures or encourage unsafe edits to satisfy a count. Compare the generated inventory to the exact locked/runtime SBOM instead.
5. **Incomplete license file handling:** runtime inventory export scans installed distribution files, but licenses may be represented by dist-info metadata, package data, bundled native libraries, OS packages or container base-image components not covered by the Python distribution loop.
6. **SBOM linkage:** the final package workflow does not in the inspected path require a complete runtime image SBOM, package-to-license mapping, or a signed attestation binding source, image digest, SBOM and exported notices.
7. **Artifact provenance and signature:** SHA-256 checksums detect accidental corruption but do not authenticate who produced the archive. A signed provenance/attestation and verification policy are still needed.
8. **Container base image scope:** the final source archive notices mention pinned external images, but the exact image digests, OS packages and their licenses must be included in the delivery's supply-chain inventory when those images are part of the delivered deployment.
9. **Placeholder review:** textual placeholder detection is narrow and should be replaced by a structured notice/manifest completeness check plus human review.

### Recommended Q16 design

- Generate source and runtime SBOMs from the exact immutable candidate and final OCI image.
- Use Syft for CycloneDX and SPDX; retain Grype output as vulnerability evidence. Treat each scan's scope and DB timestamp explicitly.
- Use ORT and/or ScanCode as independent license-analysis tools; resolve conflicts and unknowns through documented human disposition.
- Export license texts and notices for Python packages, OS packages and redistributed container components; bind every record to package/image digest.
- Replace the hardcoded 55 count with exact set reconciliation between the runtime SBOM, installed distributions and exported notice inventory.
- Generate SLSA/in-toto provenance and sign the image/archive/attestations with Cosign under a separately authorized signing identity.
- Verify signatures and provenance from a clean verifier job before packaging.
- Require exact same source SHA, tree SHA, runtime image digest, SBOM digest, evidence manifest and release artifact digest across the final gate.
- Separate `PASS_CANDIDATE`, `PASS_COMPONENT`, `PASS` and owner release authorization as distinct machine-readable states. No workflow may infer owner authorization from scanner success.

## Proposed staged plan

| Stage | Deliverable | Exit criteria |
|---|---|---|
| 0 | Q15/Q16 source assessment | Current workflow assumptions and gaps documented (this PR) |
| 1 | Q15 artifact-install prototype | Fresh ephemeral VM installs verified immutable archive; cleanup evidence captured |
| 2 | Q15 gate adapter | Canonical gate validates artifact digest, timings, health, smoke and cleanup |
| 3 | Q16 SBOM reconciliation | Source/runtime SBOMs and package/license inventory reconcile exactly |
| 4 | Q16 license review | ORT/ScanCode results, exported notices and human dispositions recorded |
| 5 | Q16 provenance/signature | Signed provenance and artifact signature verify in independent clean job |
| 6 | Final convergence | All Q10–Q16 evidence references same immutable release candidate; explicit owner authorization remains separate |

## Safety boundaries

- This is documentation-only; no build, image pull, signing, deployment or production package was performed.
- Do not run destructive database or infrastructure operations as part of Q15/Q16.
- Signing keys must never be stored in repository source or ordinary CI logs. Use an explicitly authorized, scoped signing identity only after separate approval.
- Do not change the fixed release subject or relax any gate to make the final package workflow green.
- Historical 55-distribution evidence is not current-subject Q16 evidence.
- Production remains NO-GO.
