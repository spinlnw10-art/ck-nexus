**Status:** persistent project guidance; development adoption baseline
**Owner/authority:** CK-NEXUS Core
**Last updated:** 2026-11-24

## User's standing direction
Improve CK-NEXUS continuously by discovering and using high-quality skills, plugins, coding agents, IDEs, code-generation/refactoring tools, test and security tools, performance optimizers, design systems, browser automation, API and website integrations, databases, CI and cloud systems. Prioritize speed, measurable productivity, interoperability and adaptable design.

Apply this preference across future CK-NEXUS work. Reuse prior verified assets and evidence before repeating work. Avoid producing reports that never become useful implementation; deliver working, verified capabilities in staged increments.

## Operating policy
Use `.github/skills/cknexus-ecosystem-acceleration/SKILL.md` as the reusable workflow. Discover and compare continuously, but do not install every discovered tool indiscriminately. Benchmark against current CK-NEXUS capabilities, check platform compatibility, licensing, supply-chain integrity, security, data handling, permission scope and total cost.

The weekly Ecosystem Scout is research-only. It cannot install packages, connect accounts, grant credentials, modify repositories, spend money, merge or deploy. Each adoption requires separate authorization at the applicable risk level.

## Non-negotiable boundaries
CK-NEXUS Core retains sole authority over policy, credentials, approvals, evidence, release gates, merge and deployment. External tools are subordinate. Preserve original branches, backups and evidence. Never expose secrets. Never disable security gates merely to obtain GO. Use isolated development and synthetic data only when isolation is verified; otherwise restrict experiments to read-only work and synthetic inputs. Production actions require explicit authorization.

## Evidence discipline
Distinguish DISCOVERED, EVALUATED, INSTALLED, CONFIGURED, ACTIVE and VERIFIED. Keep PASS, FAIL, NOT TESTED and BLOCKED distinct. Retain valid historical evidence; rerun only changed, expired or materially affected components. Record exact versions, source, commands, benchmark context and rollback. For the current Termux/PRoot device, consult `capabilities/system-skills.catalog.json` before using sandbox execution; a bare `unshare` canary is not proof that the full namespace/mount/chroot runner works.
